# Pact Consumer-Driven Contract Testing — Public Attestation API

This directory contains Pact contract tests that verify the contract between
**Veritasor-Frontend** (consumer) and **Veritasor-Backend** (provider) for the
public attestation API.

## Overview

Pact is a consumer-driven contract testing framework. The **consumer**
(Frontend) defines expectations for each API interaction, Pact generates a
contract file, and the **provider** (Backend) verifies that it satisfies every
interaction in the contract.

## Contract File

`tests/pacts/Veritasor-Frontend-Veritasor-Backend.json` — generated by running
the consumer tests. This file is checked into version control and published to
the Pact Broker during CI.

## Covered Endpoints

| Endpoint | Method | Status | Description |
|----------|--------|--------|-------------|
| `/api/health` | GET | 200 | Health check |
| `/api/v1/public/attestations/:hash` | GET | 200 | Valid attestation |
| `/api/v1/public/attestations/:hash` | GET | 304 | Matching ETag (not modified) |
| `/api/v1/public/attestations/:hash` | GET | 400 | Invalid hash (too long) |
| `/api/v1/public/attestations/:hash` | GET | 404 | Non-existent attestation |
| `/api/v1/public/attestations/:hash` | GET | 410 | Revoked attestation |

## How It Works

The single test in `tests/pact/contract.spec.ts` does both consumer-side
expectation definition and provider-side verification:

1. **Consumer interactions** — defines what the Frontend expects for each
   request/response pair, using PactV3 matchers for flexible field matching.
2. **Mock server execution** — each interaction is tested against Pact's mock
   server to ensure the expectations are internally consistent.
3. **Pact file generation** — Pact writes the contract JSON to
   `tests/pacts/`.
4. **Provider verification** — a `Verifier` starts the real Express app and
   replays every interaction against it, using state handlers to set up
   provider state (e.g. seed attestations in the mock repository).

## Running

```bash
# Run Pact consumer tests + provider verification
npm run pact:test

# Run with verbose output
npx vitest run tests/pact/ --reporter verbose
```

## Provider State Handlers

Each interaction may declare a `providerState` string. The verifier maps these
to state handlers defined in the test:

| State | Setup |
|-------|-------|
| `server is healthy` | Clears attestations, seeds defaults |
| `an attestation exists with hash "abc123"` | Seeds a confirmed attestation |
| `no attestation exists with hash "nonexistent"` | Removes any attestation with that key |
| `an attestation exists with hash "revoked123" and status "revoked"` | Seeds a revoked attestation |
| `an attestation exists with hash "abc123" and the request has a matching ETag` | Same as valid attestation |

## Publishing to Pact Broker

```bash
# Publish the generated contract to the broker
npm run pact:publish
```

Requires `PACT_BROKER_URL` to be set (either via environment or secret loader).

## Can-I-Deploy

```bash
# Check whether the consumer can be deployed
npm run pact:can-i-deploy
```

## Adding a New Interaction

1. Add a new entry to the `interactions` array in `contract.spec.ts`.
2. Define the `setup` (PactV3 expectations) and `test` (HTTP fetch) callbacks.
3. Add a corresponding state handler to the `Verifier` options.
4. Run `npm run pact:test` to generate the contract and verify it.
5. Commit both the test changes and the updated pact JSON file.

## Maintaining Backward Compatibility

- The contract file is version-controlled. Review changes to the JSON as part
  of code review.
- Adding new interactions is backward-compatible. Removing or modifying
  existing interactions is a breaking change.
- Use `MatchersV3.*` for fields that may vary (timestamps, IDs) to avoid
  brittle contracts.
- When the provider response format changes, update the consumer expectations
  first, regenerate the contract, then verify against the updated provider.
